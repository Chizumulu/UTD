# Lighthouse comparison

Use Actions → UTD Lighthouse comparison → Run workflow. Select a full baseline commit SHA, optionally a candidate SHA (defaults to the selected revision), and 1, 3 or 5 runs per device and revision. The default baseline is the revision immediately before the 1-H-2 JavaScript split. Pull requests modifying the benchmark itself run the same comparison automatically.

The workflow builds both revisions using their own Pages build scripts in detached worktrees on the same runner. It serves both under /UTD/ with loopback Node static HTTP servers that precompress text assets before listening (Brotli, gzip or identity via Accept-Encoding), uses Lighthouse's mobile and desktop presets with simulated throttling, alternates baseline/candidate order, and starts a fresh browser for each audit. Default: 12 audits, 3 samples per device and revision. External analytics/push URL patterns are passed as a JSON array in lighthouse-comparison-flags.json. Every report must contain all configured patterns and no HTTP responses or transferred/resource bytes for the four blocked domain families. Failed attempts may be recorded. The verification result is included in comparison.json and comparison.md. Other external resources may vary. Both servers are probed before audits for actual Content-Encoding, compressed lengths and byte-identical decoded HTML, JS and CSS. Probe evidence is saved as compression-8081.json and compression-8082.json. Already compressed images and fonts are served unchanged. Browser cache is disabled via no-store; the server precompresses assets before measurement to avoid compression CPU overhead. Local server transfer is not production CDN transfer: these results do not establish live CDN encoding, HTTP/2 behavior or real-user performance. Do not directly attribute score differences versus the previous uncompressed benchmark to production changes.

Results appear in the Actions job summary and the lighthouse-comparison artifact (30 days): individual Lighthouse JSON/HTML, comparison.json, comparison.md and server logs. Compare medians, not the fastest single run. Lower timing/transfer values and higher score are usually desirable. A percentage is unavailable for a zero baseline. The asset inventory includes optional JS/CSS and is not the initial page's total download size.

The workflow is read-only and does not publish or alter Pages. Each sample has at most three attempts (initial + two retries), with a 90-second process timeout per attempt. Runtime errors, incomplete/time-limit warnings, missing or invalid metrics, missing network requests and blocking verification failures reject a sample. The first valid report is accepted regardless of speed; exhausted attempts fail the workflow. Raw attempt reports and history.json remain under attempts/ in the artifact, including on failure. All requested valid samples are required for summary. Report per-metric min, max, median, population standard deviation and range/median; FCP, LCP, main-thread and JS execution ranges above 30% flag high variability. This is a heuristic, not statistical confidence; one sample cannot establish repeatability. Valid slow samples are never discarded merely for being slow. Build failures fail the comparison. Performance differences are informational rather than a merge threshold. Lab results do not measure real-user INP or field Core Web Vitals. The default run count is deliberately small; use five for noisier comparisons.

## Bottleneck diagnostics

Accepted reports also generate diagnostics.json (all observed rows and per-sample evidence) and diagnostics.md (top 12 rows per category, before/after medians and coverage). CPU groups, script execution, unused CSS opportunities, LCP nodes and phases, render-blocking resources, image opportunities, layout-shift nodes and network resource types are extracted from legacy Lighthouse audits and available insight details. Local benchmark ports and query strings are normalized for comparison. Missing rows or unsupported audits are not assumed to be zero; differences are shown only for complete coverage. Opportunity savings overlap, are estimates, and cannot be summed as guaranteed improvement. Listed CSS waste ratio is not the entire stylesheet inventory. This is diagnostic evidence rather than causal proof or an automatic site-code change. The pinned Lighthouse version determines available fields; inspect the raw report for unsupported insight schemas.
