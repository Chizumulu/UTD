# UTD repository instructions

## Mandatory design preservation for all optimization and improvement work
The site owner's standing instruction: preserve the existing intended visual design. Optimization and general feature/maintenance improvements do not authorize a redesign. The reference for the CSS regression correction is the original unsplit style.css and existing UI, not the incomplete cold-entry appearance introduced by PR #146.

- Preserve colors, typography, font weights, backgrounds, borders, spacing, responsive layout, sizes, icon/crest presentation, component styling, animations, and interaction states in all supported themes and languages. Do not replace the existing visual design with a simpler variant to obtain better performance scores.
- Before implementing any change that could alter visible design, first explain the affected screens/states, expected difference and reason to the owner; obtain explicit approval. Otherwise keep the existing behavior/design or omit the change. This applies to loading states, first paint, layout shifts, hover/focus/active states and delayed asset loading as well as stable screens. A proposed performance benefit is not consent.
- Shared or uncertain CSS stays critical; no extraction based only on a class-name prefix or unused-CSS report. Never rely on another screen having been visited. Do not render feature content without all required styles. Keep CSS cascade and actual computed styles intact.
- For each UI-affecting optimization, establish a pinned pre-change good-design reference; compare independent cold-entry, revisit, slow-network and relevant failure/retry states across desktop, mobile, tablet, light/dark and supported languages. Use screenshots and computed-style/layout checks with equivalent data, locale, viewport and settled rendering. A comparison of the same DOM against the current unsplit CSS tests splitting correctness only; it does not by itself prove that changes to HTML, JS, source CSS or font/image delivery preserve the pre-change design.
- Run the cold-entry CSS parity workflow and the relevant existing browser, CSS, SEO/build and feature regression checks. Preserve diagnostic evidence; do not weaken assertions, hide differences or silently accept a changed design. A visual mismatch or unexplained test failure blocks merge. Report limitations explicitly (browser profiles, external resources, data states, coverage).
- Prefer build-only/internal changes that do not modify the intended source design; prioritize design parity over byte savings or Lighthouse targets. Keep production unchanged until required tests pass and the owner approves merge.
- If the owner explicitly requests a design change, document that approved scope separately and update the design reference only after approval. Do not treat that approval as permission to redesign other screens.
